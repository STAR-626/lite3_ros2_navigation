# 开发路线与演示验收

> 第一版设计更新于 2026-10-01。除 M0 外，下面都是计划；没有人为标记尚未实现的功能为完成。整体关系见 [ARCHITECTURE.md](ARCHITECTURE.md)。

## 第一版固定范围

- Ubuntu 24.04 + ROS2 Jazzy + Gazebo Harmonic，打开 RViz 观察。
- 在终端发送目标、取消/停止、查询和手动调试指令。
- 根据 Gazebo 场景提前制作地图，使用仿真实际位姿定位。
- 复用开源 RL 训练流程，演示前训练或验证适用策略，演示时只执行策略。
- 地面可有平缓坡面和小幅起伏，但必须在 Gazebo 验证基础移动稳定性。
- 已知障碍的全局规划、临时新增静止障碍的感知与绕行、必要时重新规划、不同结果返回。
- 约 9 节点的精简设计：任务节点合并地图和启动管理，移动节点合并策略、位姿与输入模式。

下一步代码入口：先查看 `src/lite3_gazebo/CMakeLists.txt` 与 `src/lite3_gazebo/worlds/lite3_empty.sdf`，完成 M1；然后单独验证 M2，再接传感器和导航。不要跳过移动验证直接宣称导航已经完成。

地图制作可以与基础移动准备交替进行，但需要提前确定世界布局、地图原点、分辨率和机器人尺寸。

## 第一版演示场景

| 场景 | 设置 | 预期结果 |
|---|---|---|
| 已知障碍绕行 | 地图中包含墙/货架，A 到 B 有绕行路线 | 初始路径避开障碍，实际到达，`SUCCESS` |
| 轻度起伏 | 可通行路线穿过经过验证的坡面或起伏 | 稳定通过，达到目标；训练日志不能代替 Gazebo 实测 |
| 临时新增障碍 | 路径前方新增可被雷达扫描到的箱子，周围有空间 | 激光更新障碍，局部绕行或重新规划，`SUCCESS` |
| 执行途中封路 | 机器人开始移动后通道被堵，等待/替代路径尝试仍失败 | 达到阻挡处理限制后停止，`BLOCKED` |
| 初始无路可达 | 已知地图上 A 与 B 被不可通行区域完全隔开 | 初始规划无有效路径，`NO_PATH` |
| 无效目标 | 地图外或墙内的目标 | 拒绝并返回 `INVALID_GOAL` |
| 起点不匹配 | 开启起点检查并输入与真实位置不一致的 A | 不移动，`START_MISMATCH` |
| 用户取消/停止 | 行走或规划过程中发取消/停止命令 | 停止执行，返回对应状态，后续旧指令不能继续驱动 |
| 移动/系统异常 | 可控地模拟策略、传感器或定位数据失效 | 区分 `MOTION_FAILED` / `SYSTEM_ERROR`，停止任务 |
| 总超时 | 设置有限任务时长且未能及时完成 | `TIMEOUT`，终止路径跟踪 |

“无路”按当前地图、机器狗尺寸和配置定义；“被围住”作为受阻场景，不承诺自动识别其几何形状或证明永久不可达。

记录至少包含：目标、场景/地图版本、策略版本、实际路线或录像、重新规划次数、任务时长、最终结果及错误说明。位置/角度误差、最大坡度、速度、超时和重试阈值需实测后写入配置，不预先虚构指标。

## 后续扩展（有余力再做）

1. **SLAM 实时建图**：用激光逐步建图，调整地图发布和定位职责；不能让 SLAM 与原任务节点同时争用 `/map` 或同一 TF。重新统计节点数量。
2. **已知危险地形绕行**：先把陡坡、台阶、深坑等人工标为静态不可通行区域，验证规划绕行。
3. **实时危险地形识别**：评估三维雷达/深度传感器，根据坡度、高差等判断可通行性。二维激光不保证识别深坑和所有地形变化。
4. **移动障碍物**：验证随时间变化的障碍、减速、等待、绕行和更新清除。第一版新增静止箱子不等于完成此功能。
5. **自主定位**：若需要更接近真实机器人，替换 Gazebo 真值定位，评估 AMCL 或其他定位方案。

## 实施前仍需确认的工程细节

这些不改变第一版功能范围，但影响工作量和实际节点数：

- 可用 GPU、训练资源和课程时间；适用预训练权重是否存在、能否再分发。
- 官方策略的观察/动作格式与 Gazebo 关节控制方式能否对齐。
- 选择 Gazebo 插件还是 ros2_control；后者可能增加运行节点。
- 轻度起伏的具体坡度/高度，在目标仿真器中实际可通过的范围。
- 合并地图/启动管理的复杂度；若影响稳定性，允许恢复现成两个节点，采用约 11 节点备用方案。

训练与部署所用的外部源码保持独立，项目只引入必要、许可清楚的接口/资源，并记录版本。无须为落实规划而整体复制第三方仓库。
