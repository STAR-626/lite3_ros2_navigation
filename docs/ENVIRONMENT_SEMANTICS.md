# 环境语义目录：Gazebo物体与已保存地点

2026-10-20当前：bringup的DeepSeek入口默认原生工具闭环，支持环境查询、多物体串行接近和真实结果反馈；不再限制一句话一个物体。旧JSON入口可用agent_tools=false回退，原rules/非AI入口保留。临时接近的固定物体/几何限制仍在；真实API及机器狗实走待验收。见[工具模式说明](AI_TOOL_AGENT.md)。以下单动作/不支持多物体描述是前阶段记录。

2026-10-20货架编号已自动配置：`shelf_1`～`shelf_17` 对应“货架1”～“货架17”，支持“1号货架”“一号货架”等别名。当前场景标注已保存，之后无需手动定义货架A；直接输入 `去三号货架旁边` 或 `去17号货架旁边`，导航仍需先显式开启。内部Gazebo模型名不改，原自定义名字可作为别名继续使用。

2026-10-20后续：现已接入原场景固定物体的单目标临时接近点计算＋Smac可达性验证，支持“去货架A旁边”；不保存为长期地点。计算/执行移位取消，真实机器狗实走和在线模型措辞待验收。见[操作与边界](OBJECT_APPROACH.md)。下方第一步/尚未接入等文字为此前阶段记录。

## 当前实现（2026-10-20，第一步）

系统读取Gazebo场景中的顶层模型名称、实体编号、世界位置/朝向，并关联用户标注的中文名、类别、别名和用途。
已有Places文件仍管理可导航地点坐标；额外语义信息单独保存。不是相机/雷达自动识别，也没有生成巡检任务或自动计算物体接近点。

原Gazebo选点、终端坐标导航、键盘、Nav2/RL接口保持。新增功能仅在 `ai_control:=true` 的交互后台启用；
`language_mode:=rules` 完全不调用模型，适合先验证目录与标注。不开启交互后台时原系统按原方式使用。

## 实际数据路径与来源

Gazebo SceneBroadcaster 的 `/world/large_warehouse/scene/info` 服务（Empty→Scene）提供模型目录，
`/world/large_warehouse/pose/info`（Pose_V）补充模型位姿更新；只读辅助进程 `environment_transport` 输出有界JSON快照，
Python后台线程接收，ROS主线程查询时取当前快照。目录约1秒轮询，服务请求最多等待1秒；
没有有效新快照5实际秒后隐藏模型位姿，不把旧位置说成当前位置。服务错误立即标为不可用。
这不是传感器可见范围内的物体清单：读取的是仿真世界真值，包括雷达暂不可见的模型。

没有新增ROS节点：辅助进程只使用Gazebo Transport。仍通过现有
`/lite3/interaction/input` 和 `/lite3/interaction/events`（std_msgs/msg/String，JSON）交互。
后台仍是 `lite3_interaction`；stop、导航总开关、NavigateTask接口不变。

默认仓库导入17个货架、4面墙，过滤地面、Lite3、黄色/绿色展示标记和非模型灯光。
运行中GUI/CLI新增的顶层箱子可进入目录。根据 `shelf_`、`wall_`、包含box的名称建议货架/墙体/箱子类别，
其余未分类；输出 `classification_source=name_rule`，不伪称算法识别。
用户设置类别后标为user。物体名字重名或别名冲突会要求使用带来源的唯一ID。
模型数超过256或数据不合法时拒绝本次快照，不能用不完整目录证明某物体已被删除。

## 启动与逐项验证

终端1（构建安装已完成，无需再次构建）：

```bash
source /opt/ros/jazzy/setup.bash
source /home/ma/lite3_ws/install/setup.bash
ros2 launch lite3_navigation bringup.launch.py ai_control:=true language_mode:=deepseek
```

等待READY和交互后台就绪后，终端2：

```bash
source /opt/ros/jazzy/setup.bash
source /home/ma/lite3_ws/install/setup.bash
ros2 run lite3_navigation ai_console
```

若暂不调用API，终端1最后一项换成 `language_mode:=rules`，其余一致。
以下是输入ai_console的内容，不是Ubuntu shell命令；两种语言模式都在本机直接处理，不调用API：

```text
列出环境
列出类别 货架
查询物体 shelf_1
标注物体 shelf_1 名称=货架A 类别=货架 别名=一号货架,左侧货架 用途=到点巡检
查询物体 一号货架
```

预期：列出货架和墙体；`shelf_1`原点约(-2.2101,2.5934,0.03)，朝向约89.94度。
坐标是世界系；当前项目map→odom为零且odom对应world，但不能把这一点推广到任意其他场景。
`pose_world`字段顺序为[x米,y米,z米,yaw度]，它是模型原点，不是导航站立点。

已有点1时，可输入：

```text
标注地点 点1 名称=设备区检查点 类别=检查点 别名=设备区,设备柜旁 用途=设备区到点访问
列出类别 检查点
查询地点语义 设备区
设备柜旁在哪里
```

如果没有点1，先用已有存点方式创建，例如 `把当前位置设成点1`。有同名点时沿用原覆盖确认。
标注不会改变原点名、坐标、Gazebo实体名或模型显示；显示名用于目录查询和引用，原地点GUI标签仍使用原点名。
标注时只更新提供的字段，其余保留。名称/别名各最多40字符，别名最多8个；用途最多200字符。
字段含空格时使用引号包住整项，例如 `"用途=设备区 到点访问"`。
可用 `别名=` 或 `用途=` 清空对应字段。类别允许：未分类、货架、箱子、墙体、检查点、入口、等待区、充电区、普通地点。
“充电区”只表示语义类别，不代表实现自动充电；“检查点”也只表示地点，不代表完成设备故障检测。

原导航条件满足后，`去设备柜旁`可解析到已有点1，随后沿原NavigateTask执行。
`去货架A`会明确拒绝：它是物体，尚未配置安全接近点，不能把中心当导航目标。
多个对象共享别名时不猜测；用 `查询物体 model:shelf_1` 或 `查询地点语义 place:点1` 精确引用。

## 持久化与移动/删除

原 `/home/ma/.local/share/lite3_navigation/places.json` 格式不变，不自动覆盖/迁移旧地点。
语义标注默认在 `/home/ma/.local/share/lite3_navigation/environment_<指纹前16位>.json`，
完整路径在bringup的“语义标注文件”日志中打印。首次标注才创建，使用600权限临时文件并原子替换。
内容含版本、绑定指纹、按`model:模型名`和`place:原点名`关联的元数据；不保存Gazebo实时位置为永久坐标。

指纹结合地图PGM/YAML原有身份和world文件内容；改变地图或场景会选择另一份语义文件。
可通过launch的`environment_file:=绝对路径`指定文件，但绑定不符/损坏会禁用语义功能并提示，
不覆盖旧文件、不阻止原地点/导航功能。以后真正修改场景后，旧标注需要明确迁移，不能无条件套用。
不要把这个用户标注目录提交到Git作为所有机器的默认环境。

物体移动：以当前Gazebo位置查询，不保存旧坐标。物体删除：有标注的对象保留记录但present=false，无实时坐标。
场景不可用：present=null，区别于已证明不存在；保存的普通地点仍可查询。
运行时新增物体必须在当前完整快照确认存在后才能标注。重启后若动态箱子没有重新生成，标注仍在但显示不存在。
同一world内按稳定模型名称关联；Gazebo实体数字编号只作为本次运行信息，不能跨启动作为永久ID。
同名模型删除后再创建视为同一名称对应对象；要表达不同长期对象，应使用不同模型名称。

## 传给DeepSeek的信息和本地检查

只在正式DeepSeek入口的模型请求中附带环境目录：来源ID、模型/地点原名称、中文名、类别、别名、用途、
存在状态、是否为可导航地点。模型坐标不默认上传，查询位置由本机读取后返回。
用户本句或待澄清上下文本身含坐标时，这些文本仍按原协议发送；不能理解成整个API完全不发送坐标。
环境名称/标注会发送给DeepSeek；不上传PGM、SDF全文、点云、项目源码或密钥。
独立 `deepseek_preview` 不连接Gazebo，没有实时目录，只用于原独立解析预览。

允许输出新增env_list（可选category）、env_show（object）、env_label（object与至少一个标注字段）。
后台重新校验字段、真实对象存在和绑定；语言数据不被执行为shell。解析期间元数据变动会拒绝迟到结果，要求重输。
模型对“有哪些货架”“一号货架在哪里”“将一号货架叫做货架A”等自由表达的实际效果仍需用户在线验收；
本次以模拟模型验证目录确实进入请求、校验通过后查询/标注执行，不消耗真实API额度。
