**一、我们现在有哪几个包**

“包”就是把一组相关文件放在一起的项目文件夹。一个包可以包含节点，也可以只包含模型、地图和配置。

| 包 | 里面主要有什么 | 在项目里的作用 |
|---|---|---|
| `lite3_description` | URDF、四种 STL 模型、RViz 配置、显示启动文件 | 描述机器狗长什么样、身体和腿怎样连接 |
| `lite3_gazebo` | Gazebo 世界、仓库地图、仿真启动文件 | 提供机器狗运行的场景，把仿真和相关程序启动起来 |
| `lite3_control` | Gazebo 控制插件、`lite3_motion_node`、测试程序 | 接收速度指令，连接 RL 控制程序，整理机器狗的位置和状态 |
| `lite3_navigation` | 当前主要是全局规划配置 `planner.yaml` | 设置 Nav2 怎样根据地图计算路线 |

此外，我们还使用了：

```text
/home/ma/Lite3_rl_deploy
```

这个外部项目负责**运行训练好的 RL 策略，控制机器狗的腿**。工作空间里也保存了相关策略文件、修改记录和恢复资料。

我们目前使用的是训练好的策略，**没有在本项目里完成自己的 RL 训练流程**。

**二、现在已经有哪些节点**

这里要区分：**我们自己写的节点**，以及**调用现成软件启动的节点**。

目前自己写出来的 ROS2 节点是：

```text
lite3_motion_node
```

其余多数来自 ROS2、Gazebo 和 Nav2，我们负责连接、配置和使用它们。

| 节点 | 用简单的话说，它在干什么 |
|---|---|
| `lite3_motion_node` | 收到“往前走、转弯”等速度，转交给 RL；同时整理机器狗的位置，提供给导航和 RViz |
| `ros_gz_bridge` | 翻译 Gazebo 和 ROS2 的数据，让 ROS2 能读懂仿真里的时间、关节状态和位置 |
| `robot_state_publisher` | 根据机器人模型和实际关节角度，计算身体、腿、脚之间的位置关系 |
| `rviz2` | 显示机器人、地图、位置和规划路线，方便观察 |
| `map_server` | 读取已经准备好的地图，发布 `/map` |
| `static_transform_publisher` | 当前临时说明：地图坐标与我们的里程计坐标怎样对应 |
| `planner_server` | 收到目标点后，根据地图计算一条路线 |
| `global_costmap` | 给全局规划准备“哪里不能走、哪里靠障碍太近”的地图 |

**按目前的启动方式，把全局规划相关程序都启动后，大约是 8 个持续工作的 ROS2 节点。**其中 `global_costmap` 是 Nav2 内部启动的，不需要我们另写一份程序。

一次性把模型放进 Gazebo 的 `spawn_lite3` 程序，完成后会退出，不算持续工作的节点。

还有三个东西容易混淆：

- **Gazebo**：仿真程序，本身不算我们写的 ROS2 节点。
- **Gazebo 控制插件**：在 Gazebo 内部操作关节的程序，目前不是 ROS2 节点。
- **`rl_deploy`**：运行策略的外部程序，目前通过 UDP 通信，也不是 ROS2 节点。

所以，“项目用了多少个程序”和“项目用了多少个 ROS2 节点”不是同一个问题。

**三、现在已经接通的运动流程**

你在终端发出速度后，实际经过下面这条链路：

```text
终端发布速度
    ↓ ROS2 话题 /cmd_vel
lite3_motion_node
    ↓ UDP：目标前进速度、横移速度、转向速度
rl_deploy
    ↓ 读取机器狗状态，运行训练好的策略
产生 12 个关节的目标角度
    ↓ UDP
Gazebo 控制插件
    ↓ 对关节施加控制力
Gazebo 里的机器狗运动
```

举例：你发出“向前以 0.2 m/s 运动”。

这里的分工是：

1. **终端**提出要求：“向前走。”
2. **运动节点**检查指令、限制速度，并把要求交给 RL。
3. **RL 策略**结合机器狗当前的姿态、关节状态，决定腿应该怎样运动。
4. **Gazebo 插件**执行这些关节指令。
5. **Gazebo**计算机器人运动、重力和地面碰撞。

同时，还有反馈：

```text
Gazebo 里的机器狗状态
    ↓ UDP
rl_deploy
    ↓ 根据最新状态，再算下一次关节动作
Gazebo 控制插件
```

因此，RL 会不断根据状态调整腿的动作。

**训练可以提前完成，但演示时仍然需要运行策略，才能持续控制腿。**演示期间进行的是“使用训练成果”，不是重新训练。

另外，Gazebo **不直接读取 ONNX 策略文件**；读取它的是 `rl_deploy`。Gazebo 与 MuJoCo 也没有在这个流程中互相通信。

**四、机器狗的位置和画面是怎样更新的**

除了让它动，我们还要知道它走到哪里了。

目前采用的是**直接读取 Gazebo 中的真实位置**：

```text
Gazebo 的机器人位置
    ↓ /lite3/ground_truth/odom
ros_gz_bridge
    ↓ 转成 ROS2 消息
lite3_motion_node
    ↓
/odom 和坐标关系 TF
    ↓
RViz、Nav2
```

这里：

- `/odom` 告诉其他程序：机器人现在在哪里、朝哪个方向、运动速度是多少。
- TF 告诉其他程序：机器人、地图、身体、腿之间的位置关系。

当前主要坐标链是：

```text
map
  ↓
odom
  ↓
base_footprint
  ↓
TORSO
  ↓
各条腿和脚
```

可以理解为：

- `map`：地图上的位置。
- `odom`：我们用来记录机器人运动的位置参考。
- `base_footprint`：把机器狗身体投影到地面后的导航参考位置。
- `TORSO`：机器狗真实身体的位置，包含身体高度和倾斜。
- 腿和脚：根据关节角度计算位置。

腿的状态走另外一条路线：

```text
Gazebo 关节角度
    ↓ ros_gz_bridge
/joint_states
    ↓ robot_state_publisher
身体、腿、脚的位置关系
    ↓
RViz 显示机器人
```

**目前没有做 SLAM，也没有通过激光定位。**导航的位置来源是 Gazebo，符合我们第一版先简化定位的计划。

**五、现在的地图和路径规划流程**

我们当前使用的是一个仓库场景，里面有货架、箱子、围墙和地面。

对应文件分别是：

- `large_warehouse.sdf`：Gazebo 里的三维世界。
- `large_warehouse.pgm`：导航使用的二维地图图片。
- `large_warehouse.yaml`：说明地图分辨率、位置和黑白区域的含义。

**三维场景与二维地图是配套准备好的文件，目前没有实现“导入任意 Gazebo 场景后自动生成地图”。**

现在规划的流程是：

```text
地图文件 → map_server → /map
                            ↓
                    global_costmap
                            ↓
目标点 + 机器狗当前位置 → planner_server
                            ↓
                       /plan 路线
                            ↓
                         RViz 显示
```

`global_costmap` 不只是标出货架，还会在障碍周围留出一些距离，避免把机器人中心规划到贴着货架的位置。

你之前已经验证过：**从当前起点到目标点，Nav2 可以成功算出绕过货架的路线。**

但要注意：

> `/plan` 是一串“应该经过的位置”，不是“让机器人运动的速度指令”。

所以，**看到路线，说明规划成功；不代表机器狗已经会自动沿路线走。**

**六、刚完成的模式切换和停止功能是什么**

我们在已有的 `lite3_motion_node` 里增加了功能，没有为它再创建一个新节点。

它现在有两个速度入口：

| 入口 | 谁来使用 | 当前情况 |
|---|---|---|
| `/cmd_vel` | 终端手动控制 | 已接通并验证过机器狗运动 |
| `/nav_cmd_vel` | 后续导航控制器 | 接口已经做好，导航控制器还没接通 |

为了防止两个入口同时控制机器人，我们增加了两个服务：

| 服务 | 作用 |
|---|---|
| `/lite3/set_navigation_mode` | 选择接受手动速度，还是导航速度 |
| `/lite3/set_stop` | 锁定停止；明确解除后才重新接受速度 |

默认启动时是手动模式。切换模式时会先把速度清零，避免沿用之前的动作。

另外，**有效速度指令超过 0.5 秒没有更新，运动节点会持续发送零速度**。

最近完成的 18 项程序测试，验证了模式选择、超时、停止锁定和异常速度等行为。它们属于接口验证，**还没有证明完整的自动导航已经跑通**。

停止锁定目前负责阻止速度指令进入运动链路，尚未实现取消整个 Nav2 导航任务。

**七、几个重要话题和消息分别是什么**

记住这一句话：

**话题是传数据的通道，消息是通道里面传的数据格式。**

| 话题 | 消息类型 | 里面是什么 |
|---|---|---|
| `/cmd_vel`、`/nav_cmd_vel` | `geometry_msgs/msg/Twist` | 前进、横移、转向速度 |
| `/joint_states` | `sensor_msgs/msg/JointState` | 各关节的角度和运动状态 |
| `/clock` | `rosgraph_msgs/msg/Clock` | 仿真时间 |
| `/odom` | `nav_msgs/msg/Odometry` | 机器人位置、朝向和速度 |
| `/map` | `nav_msgs/msg/OccupancyGrid` | 地图上哪些区域空闲、哪些区域被占据 |
| `/plan` | `nav_msgs/msg/Path` | 规划出来的一串路线位置 |
| `/tf`、`/tf_static` | `tf2_msgs/msg/TFMessage` | 各个坐标之间的位置关系 |

你之前请求规划路线用的 `/compute_path_to_pose` 是 **Action**：提交一个计算任务，再接收结果。

模式切换和停止用的是 **Service**：提出一个简单请求，立即得到是否成功的回复。

```cpp
#include <chrono>
#include <cmath>
#include <memory>

#include "rclcpp/rclcpp.hpp"
#include "rclcpp_action/rclcpp_action.hpp"
#include "nav2_msgs/action/compute_path_to_pose.hpp"

using namespace std::chrono_literals;
using ComputePath = nav2_msgs::action::ComputePathToPose;

int main(int argc, char ** argv)
{
  rclcpp::init(argc, argv);
  auto node = std::make_shared<rclcpp::Node>("mission_manager");

  // 从终端参数读取目标；不需要用户填写起点。
  const double goal_x =
    node->declare_parameter<double>("goal_x", -3.2);
  const double goal_y =
    node->declare_parameter<double>("goal_y", -4.0);
  const double goal_yaw =
    node->declare_parameter<double>("goal_yaw", 0.0);

  auto finish = [](int code) {
      rclcpp::shutdown();
      return code;
    };

  if (!std::isfinite(goal_x) || !std::isfinite(goal_y) ||
    !std::isfinite(goal_yaw))
  {
    RCLCPP_ERROR(node->get_logger(), "目标坐标或朝向不是有效数字");
    return finish(1);
  }

  // 创建客户端，用来向已有的规划器提出任务。
  auto planner = rclcpp_action::create_client<ComputePath>(
    node, "/compute_path_to_pose");

  RCLCPP_INFO(node->get_logger(), "等待规划器，最多等待 5 秒");

  if (!planner->wait_for_action_server(5s)) {
    RCLCPP_ERROR(node->get_logger(), "没有找到规划器，请检查终端 7");
    return finish(1);
  }

  // 填写规划任务。
  ComputePath::Goal request;
  request.goal.header.frame_id = "map";

  // 零时间戳表示使用最新可用变换。
  request.goal.header.stamp.sec = 0;
  request.goal.header.stamp.nanosec = 0;

  request.goal.pose.position.x = goal_x;
  request.goal.pose.position.y = goal_y;
  request.goal.pose.position.z = 0.0;

  // 把朝向角转换成消息要求的表示方式。
  request.goal.pose.orientation.z = std::sin(goal_yaw / 2.0);
  request.goal.pose.orientation.w = std::cos(goal_yaw / 2.0);

  request.planner_id = "GridBased";
  request.use_start = false;

  RCLCPP_INFO(
    node->get_logger(),
    "请求规划：目标 (%.2f, %.2f)，朝向 %.2f rad",
    goal_x, goal_y, goal_yaw);

  // 发送请求，等待规划器确认是否接受。
  auto goal_future = planner->async_send_goal(request);

  if (rclcpp::spin_until_future_complete(node, goal_future) !=
    rclcpp::FutureReturnCode::SUCCESS)
  {
    RCLCPP_ERROR(node->get_logger(), "等待规划器接受请求时被中断");
    return finish(1);
  }

  auto goal_handle = goal_future.get();

  if (!goal_handle) {
    RCLCPP_ERROR(
      node->get_logger(),
      "规划器拒绝了这次请求，请检查是否已启用");
    return finish(1);
  }

  // 任务已接受，再等待真正的规划结果。
  RCLCPP_INFO(node->get_logger(), "规划器已接受请求，等待路线");

  auto result_future = planner->async_get_result(goal_handle);

  if (rclcpp::spin_until_future_complete(node, result_future) !=
    rclcpp::FutureReturnCode::SUCCESS)
  {
    RCLCPP_ERROR(node->get_logger(), "等待规划结果时被中断");
    return finish(1);
  }

  const auto response = result_future.get();

  if (!response.result) {
    RCLCPP_ERROR(node->get_logger(), "规划器没有返回有效结果");
    return finish(1);
  }

  // 接受任务不代表规划成功，还必须检查最终结果。
  if (response.code != rclcpp_action::ResultCode::SUCCEEDED ||
    response.result->error_code != 0)
  {
    RCLCPP_ERROR(
      node->get_logger(),
      "规划未成功：Nav2 错误码 %u，原因：%s",
      static_cast<unsigned>(response.result->error_code),
      response.result->error_msg.c_str());
    return finish(1);
  }

  // 取出规划器返回的完整路线。
  const auto & path = response.result->path;

  if (path.poses.empty() || path.header.frame_id != "map") {
    RCLCPP_ERROR(node->get_logger(), "路线为空，或路线坐标系不是 map");
    return finish(1);
  }

  const auto & start = path.poses.front().pose.position;
  const auto & end = path.poses.back().pose.position;

  RCLCPP_INFO(
    node->get_logger(),
    "获得路线：%zu 个点，起点 (%.2f, %.2f)，终点 (%.2f, %.2f)",
    path.poses.size(), start.x, start.y, end.x, end.y);

  RCLCPP_INFO(
    node->get_logger(),
    "本版只读取规划结果，没有向控制器发送行走任务");

  return finish(0);
}
```

**第二张 PPT：核心命令示例**

以下示例要求系统已经启动，RL 已进入行走状态并接管 Gazebo。每个新的 ROS2 终端先执行：

```bash
source /opt/ros/jazzy/setup.bash
source /home/ma/lite3_ws/install/setup.bash
```

启动任务管理节点，让它持续等待：

```bash
ros2 run lite3_navigation mission_manager --ros-args -p use_sim_time:=true
```

另一个终端发送目标，并接收过程反馈和最终结果：

```bash
ros2 action send_goal /navigate_task lite3_interfaces/action/NavigateTask \
  '{goal_x: 4.0, goal_y: 4.0, goal_yaw: 0.0}' --feedback
```

其中，`goal_x`、`goal_y` 是地图坐标，单位米；`goal_yaw` 是到达后的朝向，单位弧度。

假设记录的初始位置为 `(-4, -4)`，任务结束后发送返程目标：

```bash
ros2 action send_goal /navigate_task lite3_interfaces/action/NavigateTask \
  '{goal_x: -4.0, goal_y: -4.0, goal_yaw: 0.0}' --feedback
```

取消当前导航：

```bash
ros2 service call /navigate_task/_action/cancel_goal action_msgs/srv/CancelGoal '{}'
```

**取消请求被接受后，还要等待最终结果确认清理完成。** 关闭终端或按 `Ctrl+C` 不能代替取消。

锁定停止、解除锁定：

```bash
# 锁定停止
ros2 service call /lite3/set_stop std_srvs/srv/SetBool '{data: true}'

# 确认旧任务已经结束后，显式解除锁定
ros2 service call /lite3/set_stop std_srvs/srv/SetBool '{data: false}'
```

这里也要区分：**直接锁定停止只阻止速度输入，不会自动取消导航任务。** 任务取消入口才负责协调两件事。

手动模式和导航模式切换：

```bash
# 手动模式
ros2 service call /lite3/set_navigation_mode std_srvs/srv/SetBool '{data: false}'

# 导航模式
ros2 service call /lite3/set_navigation_mode std_srvs/srv/SetBool '{data: true}'
```

新任务节点会自动选择导航模式，但不会自动解除停止锁定。切回手动模式前，应先取消正在执行的导航。

手动模式下持续发送前进速度：

```bash
ros2 topic pub /cmd_vel geometry_msgs/msg/Twist \
  '{linear: {x: 0.32}, angular: {z: 0.0}}' --rate 20
```

结束这个发布命令后，运动节点超过约 `0.5` 秒没有收到新速度，就会把目标速度归零。这里的时间是输入超时，不等于实际瞬时停车。

**第三张 PPT：系统如何向用户报告结果**

| 结果编号 | 含义 |
|---|---|
| `0 SUCCESS` | 到达目标，并通过位置和朝向检查 |
| `1 NO_PATH` | 规划器没有找到有效路线 |
| `3 INVALID_GOAL` | 目标数字无效、位于地图外或占据区域 |
| `4 START_MISMATCH` | 开启起点检查后，填写起点与实际位置不一致 |
| `6 TIMEOUT` | 任务超过总时间预算，清理完成 |
| `7 CANCELED` | 用户取消，清理完成 |
| `8 SYSTEM_ERROR` | 位姿、服务、导航执行或清理过程异常 |

目前 **`2 BLOCKED` 和 `5 MOTION_FAILED` 只是预留编号**，还没有对应的阻挡重试、跌倒检测逻辑，不能在 PPT 中写成已经实现。
