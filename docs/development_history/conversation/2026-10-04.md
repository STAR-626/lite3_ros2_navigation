```cpp
        {

        {

            const auto velocity = joint.Velocity(ecm);

                !velocity || velocity->empty())

                continue;

            const double speed = velocity->at(0);

            {

                continue;
```

节点保存“当前目标速度是 0.2”。之后 RL 就可以读取这个值，计算腿怎么动。

**② 记住收到指令的时间。**

例如：“这条 0.2 的指令是刚刚收到的。”

**③ 定期检查有没有新指令。**

节点每隔 50 毫秒检查一次。如果超过 0.5 秒没有收到新指令，就认为当前速度要求过期了，把它改成零。

所以会出现两种情况：

| 你在终端做什么 | 节点怎么处理 |
|---|---|
| 不断发送“速度 0.2” | 不断更新收到时间，目标速度保持 0.2 |
| 停止发送 | 约半秒后，把目标速度改成 0 |

**为什么要做这个？** 因为我们不希望你关闭发指令的终端后，机器狗仍然一直执行最后一句“向前走”。

不过，**现在只是在节点里面保存、清零一个速度值，还没有传给 RL，机器狗不会因为这段代码就动起来或停下来。**

我们是按这个顺序搭建的：

```text
你已完成：收到速度并打印
                ↓
正在准备：保存速度，指令过期后清零
                ↓
接下来：把保存的速度交给 RL，控制机器狗
```

你现在只需要记住：**这一步是在管理“你给机器狗的速度要求”，还没开始控制它的腿。**

**1. 先把几个概念放进项目里**

| 概念 | 在这个项目里是什么意思 | 例子 |
|---|---|---|
| Package，包 | 存放相关程序、模型和配置 | `lite3_control` |
| Node，节点 | 运行起来、负责一部分工作的 ROS2 程序 | `lite3_motion_node` |
| Topic，话题 | 持续传递数据的命名通道 | `/cmd_vel` |
| Message，消息 | 某一次发送的具体内容 | “向前 0.2 米/秒” |
| Message type，消息类型 | 规定内容有哪些字段 | `geometry_msgs/msg/Twist` |
| Service，服务 | 提出一个短请求，得到回复 | “切换到手动模式” |
| Action，动作任务 | 提出一个较长任务，期间能看进度、取消，最后得到结果 | “走到 B 点” |

因此，我们会用 **Topic 传速度和传感器数据，Service 处理模式等短请求，Action 组织导航任务**。这是 ROS2 三种通信方式的典型分工。[Topic 说明](https://github.com/ros2/ros2_documentation/blob/jazzy/source/Concepts/Basic/About-Topics.rst)、[Service 说明](https://github.com/ros2/ros2_documentation/blob/jazzy/source/Concepts/Basic/About-Services.rst)、[Action 说明](https://github.com/ros2/ros2_documentation/blob/jazzy/source/Concepts/Basic/About-Actions.rst)。

一个节点可以同时订阅多个话题、发布多个话题、提供服务和处理 Action。**不用每个功能都单独建一个节点。**

这里的关节角度来自滑块窗口，**目前没有同步 Gazebo 中真实的腿部运动**。

```text
Gazebo 模拟机器狗运动
        ↓

```

这是不断重复的闭环：**读状态 → 算动作 → 执行 → 再读状态。**

其中：

- `rl_deploy` 使用 ONNX Runtime 执行策略。
- Gazebo 插件负责读取状态和执行关节动作。
- Gazebo 负责物理计算。
- MuJoCo 是之前用于验证的另一个仿真器，当前流程不需要它。

**3. 最终导航系统有哪些节点**

按我们既定的精简方案，约 **9 个节点**：

| 节点 | 收到什么 | 负责什么、输出什么 |
|---|---|---|
| `mission_manager` | 用户目标、取消/停止请求、执行反馈 | 发布地图，组织规划和执行，处理重试，返回任务结果 |
| `lite3_motion_node` | 手动或导航速度、机器人状态、模式要求 | 执行 RL 运动控制，整理位置和关节状态，处理运动异常 |
| `ros_gz_bridge` | Gazebo 的传感器、位姿和时间数据 | 转成 ROS2 能使用的数据 |
| `robot_state_publisher` | URDF 和实际关节角度 | 发布身体各部分的位置关系 |
| `global_costmap` | 预制地图、扫描数据、机器人位置 | 整理整个区域哪里能走、哪里危险 |
| `planner_server` | 目标、当前位置、全局障碍信息 | 算出一条全局路线 |
| `local_costmap` | 附近激光数据、机器人位置 | 不断更新机器人附近的障碍信息 |
| `controller_server` | 要跟随的路线、当前位置、附近障碍 | 算出当前应该前进多快、往哪转 |
| `rviz2` | 地图、激光、路线、位置关系 | 把系统状态画出来，供我们观察 |

`global_costmap` 和 `local_costmap` 分别由 Nav2 的规划服务器和控制服务器创建，不需要我们另写两套障碍处理程序。[规划服务器源码](https://github.com/ros-navigation/navigation2/blob/jazzy/nav2_planner/src/planner_server.cpp)、[控制服务器源码](https://github.com/ros-navigation/navigation2/blob/jazzy/nav2_controller/src/controller_server.cpp)。

这个数量是设计约数。原来的约 11 节点备用方案仍保留，只有地图和启动管理的合并影响可靠性时才考虑采用。

Gazebo 插件、RL 算法和 URDF 文件，不能都算成 ROS2 节点。

**4. 最终一次“A → B”是怎么发生的**

下面假设未来已经建好了场景和地图，目标 B 是地图中的某个位置。

**① 启动系统，先准备好基础数据。**

系统需要：

- Gazebo 中有机器狗、地面和障碍。
- RL 可以维持站立和基础移动。
- 地图已经加载。
- 可以读到机器狗实际位置。
- 激光数据和坐标关系正常。
- Nav2 已经准备好接收任务。

任务管理节点检查这些准备情况。**启动了程序，不代表已经可以开始导航。**

**② 你从终端发出目标。**

你发送的内容类似：

```text
目标位置：x = 8 米，y = 3 米
目标朝向：0
```

这个请求交给 `mission_manager`，拟定接口是：

```text
/navigate_task
类型：lite3_interfaces/action/NavigateTask
```

这是未来要实现的自定义 Action。

它允许任务管理节点在过程中向终端报告：

```text
正在规划
正在移动
剩余多少距离
正在重新规划
```

最后再报告成功或失败。

**③ 确定起点和目标是否合法。**

起点默认使用机器狗的**实际当前位置**。

如果你额外填写了起点，任务管理节点会检查它是否和真实位置一致。差得太大就返回 `START_MISMATCH`，不会把你填写的位置直接当成真实位置。

还要检查目标是否在地图范围内、是否落在障碍区域等。

**④ 根据地图计算全局路线。**

任务管理节点向 `planner_server` 请求：

> 请从机器狗当前位置，规划一条到 B 的路线。

规划服务器读取 `global_costmap`，考虑墙、货架、机器人尺寸和安全距离。

返回的路线可以理解为：

```text
当前位置 → 路点1 → 路点2 → 路点3 → B
```

这条路线的数据格式是 `nav_msgs/msg/Path`，里面是一串带位置和朝向的点。

规划请求使用 Nav2 的 `ComputePathToPose` Action，结果包含路线或错误信息。[接口定义](https://github.com/ros-navigation/navigation2/blob/jazzy/nav2_msgs/action/ComputePathToPose.action)。

**⑤ 把路线交给控制服务器执行。**

任务管理节点再向 `controller_server` 请求：

> 请沿这条路线移动。

使用的是 `FollowPath` Action。控制服务器在执行中反馈进度，并在结束时报告结果。[接口定义](https://github.com/ros-navigation/navigation2/blob/jazzy/nav2_msgs/action/FollowPath.action)。

注意，**路径和速度是两种不同的数据**：

- 路径：整条路怎么走。
- 速度：现在这一刻往前多快、转向多快。

控制服务器会持续根据实际位置和附近障碍，更新速度要求。

**⑥ 运动节点把速度变成腿部动作。**

导航速度经我们规划的 `/nav_cmd_vel` 交给 `lite3_motion_node`。

例如：

```text
向前 0.2 米/秒
向左转 0.1 弧度/秒
```

运动节点确认当前允许导航控制，再让 RL 结合机器狗当前状态计算关节动作。

最终：

```text
导航速度要求
    ↓
RL 算关节动作
    ↓
Gazebo 插件执行
    ↓
机器狗实际移动
```

当前 RL 仍在独立的官方程序中运行。**把 ROS2 速度接进去、逐步纳入运动节点职责，是我们接下来要实现的工作。**

**⑦ 一边走，一边读取实际状态。**

Gazebo 不断产生新状态：

- 机器狗移动到了哪里？
- 朝向变成多少？
- 腿实际转到了什么角度？
- 激光看到了什么障碍？

这些状态返回系统，使控制服务器能判断：

> 当前是否偏离路线？该继续前进还是调整方向？

所以系统不是“算一次路线后闭眼走到底”，而是持续根据反馈调整。

**⑧ 遇到临时障碍，更新障碍信息。**

例如，地图上没有箱子，但你在路上临时放了一个箱子。

```text
Gazebo 模拟激光扫描
        ↓
ros_gz_bridge 转成 ROS2 /scan
        ↓
local_costmap 更新附近障碍
        ↓
controller_server 调整速度，尝试绕行
```

全局障碍信息也需要按配置更新。局部绕不过去时，由任务管理节点组织重新规划，寻找替代路线。

有地图仍然需要激光：**地图记录预先知道的环境，激光提供当前看到的环境。**

**⑨ 到达或失败，结束任务。**

到达目标范围，返回成功。

如果受阻、发生故障或被取消，任务管理节点先终止路径执行，并让运动控制进入停止/稳定状态，再返回对应结果。

**5. 这些流程通过哪些 Topic 和 Message 连接**

下表是**当前已有和后续规划的接口汇总**，不是说它们现在全部存在。

| Topic | Message 类型 | 谁发送 → 谁接收 | 消息里是什么 |
|---|---|---|---|
| `/cmd_vel` | `geometry_msgs/msg/Twist` | 终端 → 运动节点 | 手动速度要求 |
| `/nav_cmd_vel` | 第一版计划用 `Twist` | Nav2 控制服务器 → 运动节点 | 导航速度要求，需和 Nav2 配置一致 |
| `/map` | `nav_msgs/msg/OccupancyGrid` | 任务管理节点 → 全局障碍处理、RViz | 网格地图 |
| `/scan` | `sensor_msgs/msg/LaserScan` | Gazebo 经 bridge → 障碍处理、RViz | 各个扫描方向的距离 |
| `/odom` | `nav_msgs/msg/Odometry` | 运动节点 → 导航系统、RViz | 实际位置、方向和速度 |
| `/joint_states` | `sensor_msgs/msg/JointState` | 运动节点 → `robot_state_publisher` | 关节名称、角度、速度等 |

路径显示话题方便 RViz 观察。**把路线交给控制服务器执行，走的是前面讲的 `FollowPath` Action。**

当前展示阶段的 `/joint_states` 来自 GUI；以后要换成真实仿真关节状态，避免两个来源互相冲突。

**6. 几种关键消息具体表示什么**

**`Twist`：希望怎样移动。**

我们主要使用三个字段：

```text
linear.x   前后速度，米/秒
linear.y   左右速度，米/秒
angular.z  转向速度，弧度/秒
```

它描述的是速度要求，没有目标点，也没有整条路线。

**`Odometry`：实际移动成了什么样。**

它包括位置、朝向和速度。

例如：

```text
要求向前 0.2 米/秒
实际速度只有 0.05 米/秒
位置几乎没有变化
```

导航系统就能发现机器人可能受阻。**要求的速度不能直接当作实际速度。**

第一版的位置来源是 Gazebo 真值。另外，现有 RL 的 UDP 状态包没有完整的全局位置数据，所以后续 `/odom` 还需要单独接入实际位姿，不能直接把当前 UDP 包改个名字就当里程计。

**`LaserScan`：不同方向离障碍多远。**

例如：

```text
正前方：1.2 米
左前方：3.5 米
右前方：0.8 米
```

它提供距离测量；障碍处理功能再结合机器狗位置、雷达安装位置和尺寸，判断哪些区域应避开。

**`OccupancyGrid`：地图。**

可以理解为把车间划成很多小格子，记录哪里空闲、哪里被占据、哪里未知，同时保存地图分辨率和原点。

Gazebo 的 SDF 世界文件不会自动变成这个消息。我们要制作对应的地图并发布。

**`JointState`：腿现在是什么姿势。**

里面有关节名称和对应角度等数据。`robot_state_publisher` 根据这些角度和 URDF，计算各条腿在什么位置。

**7. TF 为什么也需要**

假设激光报告：

> 在雷达正前方 1 米处看到了箱子。

导航系统还要知道：

- 雷达安装在身体哪里？
- 机器狗在地图哪里？
- 机器狗现在朝哪个方向？

否则，它无法把这个箱子正确画到地图上。

我们规划的坐标关系是：

```text
map → odom → base_footprint → TORSO → 雷达及腿部零件
```

可以分别理解为：

- `map`：整张地图的参考坐标。
- `odom`：用于记录移动的位置坐标。
- `base_footprint`：机器狗在地面上的导航参考位置。
- `TORSO`：实际机身，保留高度和倾斜。
- 雷达、腿部：相对于身体的位置。

位置整理功能负责身体在世界中的位置，`robot_state_publisher` 负责身体以下各部件的关系。**同一个位置关系不能由两个程序重复发布。**

**8. 手动控制和导航控制怎样切换**

我们保留两个速度入口：

```text
终端 ── /cmd_vel ──────┐
                       ├→ lite3_motion_node → RL → 关节运动
Nav2 ── /nav_cmd_vel ──┘
```

运动节点根据模式选择其中一个：

| 模式 | 接受什么 |
|---|---|
| 手动 | 终端的 `/cmd_vel` |
| 导航 | Nav2 的 `/nav_cmd_vel` |
| 停止锁定 | 不接受继续移动的速度要求，执行经验证的稳定停止逻辑 |

模式选择放在运动节点内部，不增加一个独立的选择节点。

你刚加的超时检查，就是其中一项基础保护。还有另一个已有保护：Gazebo 插件检查关节指令是否中断超过 250 毫秒。

两者检查的对象不同：

- **0.5 秒检查**：发送速度要求的人或 Nav2，还在发指令吗？
- **250 毫秒检查**：RL 控制程序，还在发关节动作吗？

RL 程序可能仍在正常运行，但上层已经不再发速度，所以两种检查都需要。

**9. 任务最后会返回什么**

原规划中的主要结果：

| 结果 | 意思 |
|---|---|
| `SUCCESS` | 实际到达目标 |
| `NO_PATH` | 初始规划找不到有效路线 |
| `BLOCKED` | 执行中受阻，重试或重新规划达到限制 |
| `INVALID_GOAL` | 目标不合法 |
| `START_MISMATCH` | 用户给的起点和真实位置不一致 |
| `MOTION_FAILED` | 跌倒、控制异常等运动故障 |
| `TIMEOUT` | 整个任务超过时间限制 |
| `CANCELED` | 用户取消 |
| `SYSTEM_ERROR` | 地图、传感器、坐标关系或导航服务异常 |

这些由任务管理节点统一整理，不能把所有错误都说成“没有路”。

**10. 我们现在在整个流程的哪一步**
